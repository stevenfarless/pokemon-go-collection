# Zero-cost GitHub-only architecture

This repository has a permanent product constraint: the complete core collection companion must remain buildable, deployable, forkable, and usable without paying for infrastructure outside GitHub.

Closing issue #70 means the enforcement described here has been implemented. It does not retire this rule.

## Core platform

The supported core stack is:

- GitHub repository storage for source, archived Poke Genie exports, generated contracts, retained bounded history, and documentation.
- GitHub Actions for validation, static generation, knowledge synchronization, external-data refreshes where legally permitted, and Pages deployment within GitHub Free limits.
- GitHub Pages for the published site.
- Static HTML, CSS, JavaScript, JSON, Markdown, web app manifests, and service workers.
- Browser-local capabilities such as `localStorage`, IndexedDB, Web Workers, File APIs, and WASM when useful.

The core product must not require Firebase, Supabase, hosted databases, paid APIs, paid search/vector services, serverless functions, or another owner-specific backend. Optional integrations are permitted only when the site remains usable without them and a free static fallback is documented.

## Human-facing surfaces

The generated Pages artifact exposes three primary human-facing pages:

- `/` for the searchable collection dashboard and record details;
- `/insights.html` for collection-wide summaries and drill-downs;
- `/tools.html` for owned-only planning, duplicate/trade review, local annotations, goals, what-if calculations, and freshness-gated current-event planning.

These pages consume the same build identity and canonical resource set. They must not become independent applications with competing identity, species, freshness, or recommendation semantics.

## Data and privacy boundary

Poke Genie exports are archived unchanged under `exports/`. The production build derives normalized static resources from the newest valid timestamped export. `data/pokemon.json` is the canonical complete owned-record dataset for a build.

Canonical record identity and provenance are generated by the build. Browser-local saved views, goals, notes/review labels, column preferences, and similar personal state remain separate from generated collection facts. Record-specific annotations use canonical record identity and explicit migration/ambiguity handling. Browser-local state is not written back into `pokemon.json` and is not sent to an application backend.

No core workflow requires account credentials, external API keys, or repository secrets beyond GitHub's built-in Pages/OIDC permissions.

## Data layers

The architecture deliberately separates different kinds of information:

1. **Owned collection facts**: normalized from the selected Poke Genie export and published under `data/`.
2. **Stable species/mechanics knowledge**: versioned, pinned, provenance-carrying community data under `data/knowledge/`.
3. **Derived collection intelligence**: deterministic recommendations, candidate feeds, investment inputs, reasoning traces, views, species/family resources, and bounded history derived from the owned collection and stable knowledge.
4. **Current rotating game data**: freshness-aware external snapshots for categories such as events, raids, PvP, Rocket, Max Battles, and moves. Current-data consumers must block or degrade when required snapshots are stale, expired, failed, or unavailable.
5. **Browser-local user state**: saved views, goals, annotations/review labels, and preferences, kept separate from generated public collection resources.

A consumer must not silently promote one layer into another. For example, a Poke Genie PvP IV percentile is not a current-meta ranking, and a browser-local note is not a Poke Genie fact.

## Machine-facing surfaces

Machine clients may use:

- `data/llm-bootstrap.json` and `llms.txt` for compact discovery;
- `data/build-manifest.json` for authoritative build identity and public-resource inventory;
- `data/pokemon-index.json` plus bounded `data/pokemon/chunk-NNNN.json` shards for full-collection retrieval without relying on one large payload;
- species/family resources and derived views for selective retrieval;
- `api/v1/` for stable versioned static endpoint paths;
- bounded history and collection diffs;
- recommendation, candidate, investment, reasoning, knowledge, and external-freshness resources where relevant.

All of these remain ordinary static files. There is no runtime query server or hosted database.

## Fork/bootstrap contract

A fresh public fork must be able to reproduce the project using a GitHub Free account:

1. Fork the repository.
2. Keep GitHub Actions enabled.
3. In repository Settings > Pages, use **GitHub Actions** as the Pages source.
4. Add a Poke Genie CSV under `exports/` using the supported `shared-text-YYYY-MM-DD HH_MM_SS.mmm.csv` filename pattern.
5. Run the validation workflow or open a pull request.
6. Merge/push to `main`. The Pages workflow builds an isolated candidate, validates it, promotes only a healthy artifact, and retains bounded last-known-good rollback artifacts.
7. Confirm `data/build-manifest.json` identifies the expected export, build ID, counts, and published resources.

No custom domain, external database, SaaS account, API key, or paid service is required.

## Enforcement

`scripts/check_architecture.py` runs in validation and deployment. It fails when the core runtime introduces known hosted-backend dependencies, owner-provisioned workflow secrets, or other prohibited required-service indicators.

The check is intentionally conservative rather than pretending static analysis can prove every architecture property. Code review must still verify that new features:

- have a bounded storage and Actions-cost strategy;
- keep generated history, caches, and artifacts from growing without limit;
- use repository-hosted snapshots for current data when legally and technically practical;
- degrade explicitly when optional external/current data is stale or unavailable;
- do not make a paid LLM or another external service necessary for core calculations;
- preserve fork-friendly relative paths and avoid owner-specific infrastructure;
- preserve canonical record identity and source/provenance boundaries rather than inventing competing local systems.

## Architecture review for future issues

Before an issue is considered complete, any infrastructure choice must satisfy this policy. A feature that cannot fit the constraint must be redesigned as static/client-side, made optional with a complete free fallback, or rejected/superseded.

The authoritative product requirement remains issue #70 plus this document. A later change to the constraint requires an explicit repository-owner decision and corresponding documentation update.
